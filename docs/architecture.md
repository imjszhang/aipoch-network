# 架构与决策

状态：规划基线，尚未实现。日期：2026-09-12。

## 1. 项目定位与成功标准

AIPOCH Network 是以 GitHub 为来源、身份和协作基础的科研项目与资源目录。它把原有资料整理成可发现、来源明确、能够被人和独立软件消费的科研信息。

首要目标是降低现有项目与组织的参与成本。基础收录只要求一个有效公开 GitHub 链接，不要求作者迁移仓库、注册新账号、编写专用清单、改变许可证或适配工作台。信息不足可以显示为未知；进一步补充描述与接入能力是可选增强。

第一版应完成两个互相独立的场景：

- 普通访客无需账号和工作台，即可找到条目、理解用途及信息来源、访问原项目、下载入口和原协作渠道。
- 任意客户端仅依赖公开说明和静态目录，即可定位资源及指定来源版本。该客户端不存在或升级时，目录网站仍然能够构建、测试和发布。

## 2. 范围

### 第一版包含

- GitHub 公开仓库、公开个人/组织资料的候选收录；组织仓库的选择性策展。
- 研究项目、可复用资源、个人/组织和专题集合的关联浏览。
- 来源明确的补充描述、科研分类、版本与访问条件说明。
- 静态搜索、筛选、详情、来源与下载链接。
- GitHub Issue/PR 投稿和修订流程；当前私有开发期先验证内部模拟流程，公开投稿在可见性决策后验收。
- 有缓存和失效状态的批量采集、可重建快照、公开静态目录契约。
- 人工审阅的维护者与组织确认记录。

### 第一版不包含

- 自建常驻后端、账号密码服务、即时消息、个性化在线推荐、设备在线状态和任务分发。
- 私有研究数据托管、机构细粒度权限体系、模型推理或研究代码执行。
- Open-Science 专用 Connector、协议、插件或任何客户端内部格式。
- 全量 GitHub 抓取、原仓库镜像、大文件托管、GitHub 以外来源适配和多目录联邦。
- 自动科学认证、声誉排名、商业交易和结算。

未来贡献和复现证据可以按通用关联记录扩展；不能把 CI 检查通过、被目录收录、Star 或 Fork 数当成科学验证结果。

## 3. 单仓库模块结构

| 模块 | 输入 | 输出 | 不应承担的职责 |
| --- | --- | --- | --- |
| `registry/` | 候选来源、人工编辑、认领证据、专题选择 | 审核后的目录引用和覆盖式补充资料 | 保存 GitHub 令牌、完整上游副本或生成搜索索引 |
| `spec/` | 目录自身的业务概念与兼容性要求 | 数据定义、公共格式、语义规则、样例 | 镜像某个客户端的数据结构 |
| `pipeline/` | 注册目录、公开 GitHub 观察值、缓存 | 归一化来源、有效快照、公共目录、内部搜索数据 | 执行上游研究代码、从访客浏览请求触发采集 |
| `web/` | 已生成的公开数据与内部搜索索引 | 可静态托管的页面和浏览器交互 | 服务端会话、凭据交换、实时 GitHub 查询依赖 |
| `design/` | 用户提供的 HTML 设计交接文件 | 原件档案、当前基线、版本差异和页面实施映射 | 生产入口、已实现功能证明或可执行指令 |
| `generated/` | 固定输入快照和生成配置 | 可重建构建产物 | 充当唯一历史记录或人工编辑入口 |
| `docs/` | 设计与运营决策 | 可执行计划、贡献指南、消费说明、排障和回滚说明 | 声称未实现的功能已存在 |
| `.github/` | 已授权的 GitHub 协作与自动化需求 | 无凭据 PR 检查、受信采集、受控发布 | 在当前规划阶段启用公开部署 |

后续实现从一个根工具链开始。暂不引入 workspace 包拆分、独立 SDK 仓库或共享客户端源码；只有实际复用和独立发布需求出现时再评估。

## 4. 三层数据与两种输出

### 4.1 原始来源观察层

读取 GitHub 的仓库稳定标识、当前地址、公开元信息、默认分支、指定版本的必要资料等。记录观察时间、来源位置和适用版本。原仓库继续拥有文档、代码、发布及协作。

不要求先复制上游完整历史。研究包和较大文件继续链接原仓库、Releases 或原托管位置。

### 4.2 目录编辑层

保存 AIPOCH 自己维护的收录引用、科研领域、类型、用途描述、专题关系以及有证据的认领状态。每项补充区分自动提取、社区编辑和维护者声明。

刷新上游资料不能覆盖人工描述；人工文字也不能静默伪装成上游作者原话。冲突需要保留来源并按字段规则处理。

### 4.3 派生发布层

从确定的来源快照和目录修订生成规范化条目、关联、索引和页面数据。生成结果附上数据修订、构建版本与更新时间。相同固定输入可重建等价语义输出；生成时间等非确定字段需要单独处理。

### 4.4 面向第三方的公共目录

拟定入口为相对发布根的 `catalog/v1/manifest.json`。入口描述当前有效快照和相对位置的分片、详情数据。语义及兼容性由 `spec/` 负责，具体字段见 [目录契约](catalog-contract.md)。该路径当前尚未实现。

公共契约使用通用科研对象与来源引用，不包含客户端私有字段。新版本发布前要验证旧消费者；不兼容变更引入新的主版本入口。

### 4.5 网站内部搜索输出

搜索分词、排名权重、压缩形式和缓存格式是 `web/` 与生成器内部约定，不属于公开协议。替换搜索库或改页面框架不能迫使外部消费者升级。

## 5. 对象、身份与版本

来源仓库、研究项目和可复用资源分别建模。一个仓库可以提供多个资源，一个研究项目也可以引用多个仓库。组织和个人延续 GitHub 身份，研究档案属于带来源说明的补充资料。

基础收录阶段允许类别待定、许可证未知、版本未固定。目录接受不代表可以再分发或自动执行。只有需要精确复用时才要求明确的 commit、路径及可验证内容引用；能力不能确认时只提供阅读来源与下载说明。

GitHub 用户名、组织名和仓库名称可以变化；内部稳定条目标识、GitHub 稳定 ID、当前显示地址与历史别名需要分开。原名称被其他对象重新使用时，不能把它自动认作旧来源。

社区收录不会把组织标成正式加入；公开组织成员身份不等于组织授权。认领要限定到实际被证明的仓库或组织范围，并保留证据、审核人和时间。

## 6. 独立网站与公开链接

第一版前端以用户指定的 [aipoch-network-concept-v6.html](../design/references/aipoch-network-concept-v6.html) 为页面结构、视觉和交互意图基线。后续仍通过用户提供的新版 HTML 更新设计，按 [设计交接规则](../design/README.md) 保留原件、记录替代范围和实现状态。该选择取代从零制定视觉方案的计划，不改变既定的数据与独立性边界。

网站的首批核心入口为发现、项目、资源、组织和专题集合。个人资料可作为作者/维护者详情呈现，暂不创建独立社交账号中心。

原型中的账号、连接工作台、发布和个人状态需要逐项映射到实际首版能力；模拟交互不证明后端存在。实施时保持设计结构与意图，记录因 GitHub 复用、静态托管或客户端独立性产生的必要调整，不将示例机构、数据和成功提示当作生产事实。

访客可以匿名完成浏览与来源跳转。投稿页面解释 GitHub 流程；公开入口尚未就绪时必须明确其限制，不显示能成功提交的假表单。

稳定条目链接用于分享和第三方读取。第一版不依赖特定客户端唤起协议、不检测工作台安装状态、不读取客户端会话。Open-Science 未来可以在自己的 Connector 中识别这些链接。

拟采用预生成详情 HTML 与静态目录路径，React 提供搜索和筛选交互。Pages 项目站的子路径、直接打开、刷新、分享链接和找不到条目的页面需要真实静态服务验证；不能假设托管方提供 SPA history 回退。

显示源内容时进行链接协议检查和 Markdown/HTML 清理。缺失、过期和撤回状态必须在界面可见，不能渲染为空白成功页。

## 7. 建议技术基线

以下是启动实施时的建议选择；P1 确认可构建的最小方案并锁定实际版本。当前不安装依赖、不生成应用脚手架。

| 领域 | 建议 | 选择理由与验收 |
| --- | --- | --- |
| 语言与工具链 | TypeScript，受支持的 Node.js LTS，npm 锁文件 | 一个仓库可同时维护生成器与前端；运行时和依赖版本在 P1 固定 |
| 网站 | React + Vite，静态产物 | 不需要服务端运行时；必须验证 Pages 子路径与预生成详情路由 |
| 收录源格式 | 简明 JSON，字段表和 JSON Schema | 能被 GitHub PR 审阅；Schema 之外另做引用、身份与权限语义检查 |
| 搜索 | 构建时生成的 MiniSearch 索引 | 初期不维护搜索服务；中文分词必须单独验证，体积和移动端内存决定是否分片 |
| 流水线 | Node.js 批处理，优先 GitHub REST | 只按登记来源采集；处理分页、条件请求、限额和缓存 |
| 验证 | 模型/流水线单元测试，静态站点浏览器测试 | 默认离线 fixtures，无客户端和 GitHub 凭据依赖；少量 live smoke 显式开启 |
| 自动化 | GitHub Actions | PR 检查、受信采集、发布分离，当前尚不启用部署 |

默认保持来源原语言。第一版界面沿用 HTML 基线的英文与文案语气，功能相关文字按真实能力和范围调整；保留本地化边界，中文与英文资料搜索使用代表性样例验证。第一版不自动批量翻译所有科研资料，界面语言不作为目录收录门槛。

为防止不必要的提前优化，规模测试采用 100、1,000、10,000 条合成与代表性混合 fixtures。P2/P3 记录压缩大小、生成时间、首屏与查询延迟，明确目标设备和网络条件后设置门槛。通过分片和减少首屏数据控制增长；达到静态目录能力边界后再评估替代方案。

技术依据：[Vite 静态部署](https://vite.dev/guide/static-deploy.html)、[MiniSearch](https://lucaong.github.io/minisearch/)、[MiniSearch API](https://lucaong.github.io/minisearch/classes/MiniSearch.MiniSearch.html)。官方平台限制核验见 [交付与运营](delivery-operations.md)。

## 8. 采集、失败与公开发布

主要路径为候选提交、审核目录修订、受信来源刷新、生成一致快照、检查产物、发布完整版本。浏览器不为每位访客重新查询 GitHub。

周期刷新为尽力调度，支持手动重跑。瞬时失败保留最后有效结果并标记过期；源删除、撤回、转私有等情况单独处理。历史快照保留政策必须允许撤回敏感资料的例外，不能把永久公开缓存作为不可变版本的副作用。

从同一数据修订构建网站和公共目录，检查通过才切换有效发布。回滚使用已核验的完整构建版本；重跑采集与恢复发布不是同一件事。详情见运营文档。

## 9. 私有阶段与公开参与

当前主仓库保持私有，仅创建文档；没有 Pages、在线预览或对公众可写入的入口。未来公开试点前必须决定：

1. 主仓库整体公开，使代码、目录、投稿和构建继续在一个仓库；这是简化运营的首选提案，尚未得到公开授权。
2. 主仓库长期私有，另外创建公开目录/投稿仓库；这会增加跨仓库格式、凭据、触发与同步边界，需先补充设计和授权。

不要把私有源仓库与私有站点混为一谈。公开前检查完整 Git 历史、凭据、附件、对外身份声明和许可方式；测试外部非协作者能实际完成投稿。

许可证分开处理本站代码、AIPOCH 原创目录文字与上游引用。收录链接不改变上游代码或文档许可证；缺少许可证不妨碍展示公开来源，但不能据此承诺可复制、分发或运行。
