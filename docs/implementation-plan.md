## 1. 项目目标与架构边界

AIPOCH Network 是独立的科研项目与资源目录，复用 GitHub 已有的仓库、组织、作者、版本和协作关系。网站计划采用静态生成方式，后续可部署在 GitHub Pages；内容采集、检查和构建通过 GitHub Actions 等离线流水线完成，无需维护常驻业务服务器。

首要目标是：**一个没有为 AIPOCH 做过适配的现有公开 GitHub 项目，仅凭链接就能被收录并有用地展示。** 维护者可以继续在原仓库工作，也可以选择补充科研描述或增强资源清单。

核心边界如下：

1. 原项目继续拥有代码、文档、发布版本和协作空间，AIPOCH 维护引用、科研分类和补充说明。
2. 仓库、研究项目与研究资源不是一对一关系。一个仓库可以提供多个资源，一个研究项目可以关联多个仓库。
3. 身份延续 GitHub，主动参与、社区收录和维护者确认具有不同状态。收录不表示组织加入、合作关系或科学背书。
4. 来源数据、人工补充和派生产物分层保存，来源更新不覆盖人工维护内容。
5. 网站独立提供发现、阅读、来源访问、下载跳转、投稿跳转和协作跳转，不要求安装任何工作台。
6. 公开静态契约属于 AIPOCH 自身。第三方客户端负责将其适配到自己的项目、技能、工作流和执行环境。
7. **AIPOCH 不依赖 Open-Science 的代码、内部类型、配置格式、数据库、运行状态、版本或发布时间。** Open-Science 只是潜在消费者之一，其适配不属于本项目的完成条件。
8. 资源被收录与资源可自动执行是不同能力。首版不承诺自动运行任意科研仓库。

## 2. MVP 范围与非目标

### 2.1 MVP 必须交付

| 范围 | MVP 行为 |
| --- | --- |
| 最小收录 | 接受公开 GitHub 仓库链接；没有专用清单也能建立条目，缺少信息明确标为未知 |
| 科研分类 | 人工维护研究领域、适用问题、资源类型和集合；保留信息出处 |
| 关系表达 | 表达项目、资源、来源仓库、作者/组织及集合之间的关联 |
| 来源刷新 | 定期整理公开元数据和适量说明内容，记录采集时间、来源版本与异常状态 |
| 独立网站 | 发现、搜索、筛选、项目/资源详情、组织来源页、专题集合与来源入口 |
| 原站操作 | 下载、查看代码、讨论和参与贡献尽量跳转原仓库现有入口 |
| 投稿维护 | 在确定公共协作位置后，通过 GitHub Issue/PR 完成投稿、修正和目录更新 |
| 公开数据 | 版本化静态目录和通用消费文档；与网站内部搜索索引分离 |
| 运营基础 | 清晰的收录规则、来源纠错入口、刷新状态、发布回滚与维护说明 |

试点暂按 20–30 个公开来源仓库、至少 3 个组织来源和若干科研分类规划。必须包含：无需适配的传统科研仓库、同仓库多资源、跨仓库研究项目、信息缺失、归档与失效来源。数量是试点假设，可在 P1 根据实际内容调整。

### 2.2 首版不做

- Open-Science Connector、桌面唤起专有协议、客户端在线状态、客户端授权及本地项目管理。
- 独立账号密码体系、私有研究数据托管、机构内部权限系统或即时消息服务。
- 自动运行或安装被收录仓库的代码，不把目录构建变成科研执行平台。
- 镜像全部代码、数据集和发布附件，不承担原站所有内容的长期分发。
- 科研信誉评分、结论真伪认证、将 Star/Fork 数直接换算为复用或验证次数。
- 完整社交网络、实时动态流、个性化推荐和复杂关注系统。
- 多代码托管平台的完整适配、多目录联邦或独立 SDK；数据设计保留扩展空间即可。
- 商业交易、付费访问和订阅计费。

## 3. 计划中的项目结构

保持一个独立主仓库，先按职责拆分目录，避免初期跨仓库发布协调。

| 路径 | 计划职责 | 不应承担的职责 |
| --- | --- | --- |
| `web/` | 网站页面、交互、无障碍与展示 | 维护另一套资源模型或依赖某个客户端 |
| `registry/` | 人工维护的来源引用、条目、组织选集、专题和补充说明 | 存储令牌、原始研究数据或整仓镜像 |
| `spec/` | 规范、版本规则、校验模式、兼容样例 | 引入 Open-Science 内部类型 |
| `pipeline/` | 采集、规范化、检查、派生与构建 | 执行被收录仓库提供的脚本 |
| `generated/` | 可重建的快照、页面数据、内部索引和公开静态数据 | 成为需要人工直接修改的事实源 |
| `docs/` | 产品、架构、投稿、维护、消费接口和实施文档 | 宣称尚未实现的功能已可用 |
| `.github/` | 投稿/PR 模板、检查、刷新和发布工作流 | 在不可信投稿上下文中暴露写入凭据 |

测试和样例随对应模块组织。`generated/` 已列入忽略规则，是逻辑产物边界，不作为人工维护的 Git 数据源。P1 明确快照的保存位置和保留期；原始采集缓存不进入未来公开 Git 历史，只有经过审查的合成/脱敏 fixture 可随对应模块提交，避免体积增长和撤回困难。

数据流为：

**GitHub 公开来源 → 采集快照 + 人工注册目录 → 规范化目录 → 网站内部索引与公开静态契约 → 网站和独立消费者。**

网站内部搜索结构可独立变化。对外消费者读取 P1 定义的版本化公共契约，P5 只验证其可消费性和兼容性，不再设计第二套模型。

数据格式细节在 [目录与公共契约方案](catalog-contract.md) 中维护，权限、刷新、投稿和发布细节在 [交付与运营方案](delivery-operations.md) 中维护。本计划负责阶段、依赖、交付与验收；三份文档同步演进，避免各自定义不同的模型或完成标准。

当前技术候选为 TypeScript、Node.js LTS、React/Vite、JSON Schema 和 MiniSearch，P1 先用小范围原型验证静态产物与路由，再锁定具体版本。公共契约拟以 `catalog/v1/manifest.json` 为入口，具体结构按契约文档在 P1 定稿。详情页应生成可直接访问的静态路由，不假设 Pages 提供单页应用回退。

## 4. 私有开发与未来公开的决策

### 4.1 当前约束

当前仓库保持私有，仅用于规划和后续开发。P0 不启用 Pages、不创建公开入口、不转公开、不发布演示站点。私有仓库状态与未来站点输出的可见性是两个独立问题，不能相互推断。

### 4.2 未来首选方案，尚待用户决定

在准备公开试点时，**优先评估将主仓库整体公开**，使代码、目录、投稿与构建保持统一。该方案尚未获得执行授权。

决策前应提供可审查的公开内容清单，并检查完整历史、配置、样例、内部记录、个人信息和凭据痕迹；同时明确本项目代码与目录内容的许可证。上游资源的许可证继续独立适用。发现历史内容不适合公开时，应提出保留私有历史、另建干净公开仓库等具体替代方案，不自行改变公开性。

### 4.3 如主仓库长期私有

需新增公共目录或投稿仓库，使外部用户能够浏览规则、提交 Issue/PR 和参与审核。新增以下实施项后，才能宣称社区投稿闭环已完成：

- 明确公共目录和私有代码各自的事实源、维护者和发布责任。
- 定义公共目录格式版本与私有构建代码的兼容关系。
- 设计最小权限的读取、同步、触发和发布链路，并记录凭据归属与轮换方式。
- 防止公开投稿修改私有执行代码、获得写令牌或读取私有仓库内容。
- 规定同步冲突、构建失败、撤回投稿和仓库不可用时的恢复流程。
- 重新验证从外部普通 GitHub 账号提交到目录发布的完整路径。

该分仓方案增加维护成本，不作为当前默认已执行事项。P6 启动部署前，还需核验当时 GitHub 账号套餐、Pages 对私有源仓库的支持、站点可见性和相关平台限制。若用户尚未决定公开方式，开发可以推进到本地发布候选，但不能完成公共发布验收。

**完成标准：**

- 只有公开仓库 URL 的条目可通过最小格式校验；缺少专用清单、Topics、标准目录或许可证文件不会成为隐藏的接入门槛。

- 一个仓库可对应多个资源；一个项目可关联多个仓库，且不重复创造来源身份。
- 来源字段、人工描述和自动推断的出处可追踪，覆盖规则有冲突样例。
- 公共契约有独立版本，额外可选字段不会破坏旧消费者；不包含客户端内部类型或配置依赖。
- 网站内部索引、公共契约、人工事实源和生成产物职责清楚；所有必要技术决策可在独立仓库内实现。

**失败与回滚：** 若真实试点无法用最小格式描述，先修正模型和样例，再开始采集与页面实现。尚未公开的草案可集中调整；一旦作为公共版本发布，则按版本策略演进，不能覆盖原格式后要求所有客户端同时升级。

**失败与回滚：** 采集失败保留最后有效快照；输入或契约检查失败时中止新产物发布，保留上一版。删除或撤下条目保留必要的失效标识和引用解释，避免静默将旧链接指向其他来源。

- “社区收录”“维护者确认”“组织主动策展”等状态不会被视觉设计合并为统一认证标志。
- 搜索与主要页面使用静态产物，不要求每名访客逐个调用 GitHub API。
- 不存在下载地址、许可证未知或能力未描述时，提供准确状态，不创造自动运行或自由分发的承诺。
- 常见屏幕尺寸与键盘路径可使用；在无单页应用回退的静态托管环境中直接打开详情 URL 和刷新页面正常；站点构建没有客户端服务地址依赖。

**失败与回滚：** 以 P1 固定样例继续开发，不为页面方便另建模型。搜索失败时仍可浏览分类和条目；新版页面构建或关键路径验证失败时保持上次可用站点产物。本阶段仅本地验证，不自行发布公共预览。

### P4：GitHub 投稿、治理与组织接入

**状态：未开始。**

**目标：** 建立低门槛且可维护的社区投稿、信息修正和组织策展流程，延续原项目协作关系。

**前置依赖：** P1 收录规则与最小格式完成；自动检查依赖 P2。公共端到端验收还依赖用户决定公共协作位置。

| 任务 ID | 任务 | 具体交付 |
| --- | --- | --- |
| P4-01 | 制定收录、修正、撤下与重新收录规则 | 贡献指南、审核清单、纠错/撤下流程与责任说明 |
| P4-02 | 提供最小投稿和改进模板 | GitHub Issue/PR 模板、示例和维护者操作指南 |
| P4-03 | 为投稿接入自动检查 | URL/重复/模式/引用检查；不可信投稿与特权发布分离 |
| P4-04 | 实现维护者确认和组织策展规则 | 确认依据、确认范围、撤销机制与组织集合维护方式 |
| P4-05 | 验证外部参与与原站协作闭环 | 普通外部账号投稿演练、目录修正演练、原项目协作跳转检查 |

**完成标准：**

- 提交链接是最小动作；无需修改上游仓库、安装应用或采用 AIPOCH 清单。
- 普通 GitHub 用户可在实际公共入口完成投稿并获知审核结果；没有公开入口时明确记录此项尚未通过。
- 重复条目、缺失来源和描述争议有具体处理路径，不依赖维护者凭记忆处理。
- PR 作者身份、仓库维护权限和组织代表权限分别核验；社区贡献者不能仅凭修改描述认领组织。
- 组织主动接入支持选择仓库或资源范围，不默认整组织公开仓库全部正式加入。
- 研究问题与代码改进继续指向原项目，目录描述错误回到目录维护入口。
- 检查第三方 PR 时不暴露私有内容或写入凭据，获批目录进入受信任构建后再发布。

**失败与回滚：** 有争议的组织确认和条目修改可回退到上一个审核版本；来源事实和争议说明保留。公开方式尚未决定时，先完成模板与本地流程设计，不自行创建公共仓库或改变私有仓库权限。

### P5：公共契约消费、独立性与兼容验证

**状态：未开始。**

**目标：** 证明 P1 公共契约能够被独立消费者使用，且网站内部和外部客户端可以各自演进。

**前置依赖：** P1-05 定义契约；P2 提供实际产物；P3 提供网站集成结果。

| 任务 ID | 任务 | 具体交付 |
| --- | --- | --- |
| P5-01 | 编写通用消费者文档 | 公共入口、字段、版本、分页/分片、错误状态和缓存使用说明 |
| P5-02 | 建立最小独立消费样例 | 只依赖公开文档和静态数据的读取/查询/版本定位检查 |
| P5-03 | 验证向后兼容和废弃机制 | 旧样例消费新可选字段、未知字段处理、格式版本检查 |
| P5-04 | 验证与网站实现、工作台完全解耦 | 不启动任何客户端服务的构建、测试、消费与发布候选验证 |
| P5-05 | 核对发现与固定版本引用的区别 | 最新来源刷新、特定版本引用、失效引用和校验信息的检查 |

**完成标准：**

- 一个未读取网站实现的独立消费者可按文档列举资源、理解关系并定位来源及已声明版本。
- 更换网站内部搜索索引格式，不改变公共契约和消费者结果。
- 公共格式新增可选字段时旧消费者仍可运行；破坏性变更具有新版本或明确兼容处理。
- 项目的安装、测试、构建及站点运行不依赖 Open-Science 代码包、共享类型、文件路径、深链接协议、在线状态或发布节奏。
- 固定版本信息缺失时明确为未固定，不用当前默认分支冒充已验证快照。
- 所有公共消费内容来自 P1 模型和 P2 产物；没有为某个客户端再维护第二套事实源。

**失败与回滚：** 出现文档与产物不一致时修正同一契约或实现，再重新验证；不能用客户端私有补丁掩盖公共契约问题。已发布格式保持可用，破坏兼容的候选产物不得覆盖原入口。

### P6：试点、发布候选与运营交接

**状态：未开始。**

**目标：** 完成多类真实来源试点、恢复演练和公开发布准备；公开操作仅在用户选择的方案获得授权后进行。

**前置依赖：** P2、P3、P5 的必要验收与 P4 的规则、模板、本地检查通过。P4 的外部公共投稿演练可以在本阶段公开入口获授权并就绪后补齐，不作为准备公开决策材料的前置，避免阶段循环依赖。公共发布还依赖公开方式、站点域名/地址及发布权限决定。

| 任务 ID | 任务 | 具体交付 |
| --- | --- | --- |
| P6-01 | 整理试点内容并开展全链路验收 | 试点目录、来源审核结果、场景矩阵与缺陷清单 |
| P6-02 | 准备仓库与站点公开决策材料 | 公开内容/历史检查、许可证、账号套餐与 Pages 能力核验、可审查的部署方案 |
| P6-03 | 在获得授权后设置部署与刷新 | Pages 发布工作流、定期刷新、并发控制、产物版本与权限设置 |
| P6-04 | 演练故障和恢复 | 来源限流、部分采集失败、坏条目、构建失败和版本回滚记录 |
| P6-05 | 完成运营交接和发布后核验 | 维护手册、责任分工、指标、更新节奏、外部访客与投稿者验收结果 |

**完成标准：**

- 核心试点场景全部有实际结果，没有以内部维护者权限替代外部投稿者验证。
- 公开方式经用户决定，实际源仓库可见性、投稿入口可见性、站点可见性分别检查。
- 从条目提交、审核合并、生成索引到网站更新的链路可重复运行。
- 最近有效版本可恢复；刷新失败不会将全站变成空目录；产物显示更新时间。
- 维护者能按手册处理过期来源、重复条目、描述纠错、撤下请求和构建失败。
- 发布结果无需任何工作台在线，公共静态数据与页面同时完成验证。
- 若未授权公开，只能完成“本地发布候选与决策材料”，P6 公共发布相关事项继续标为未完成。

**失败与回滚：** 新发布出现关键缺陷时回滚到已验证产物；停止故障刷新，保留诊断并修正后重试。仓库转公开可能已经形成外部副本，不能将改回私有当作撤销公开内容的保证，因此公开前完成内容与历史审查。

## 6. 跨阶段依赖与可并行工作

| 工作 | 必要前置 | 可以并行 | 合并或进入下一阶段的条件 |
| --- | --- | --- | --- |
| P1 模型与契约 | P0 | 技术选型、试点来源整理、治理原则细化 | 最小样例与关系样例全部可表达 |
| P2 采集与生成 | P1 模型/契约 | P3 基于固定样例的页面开发、P4 投稿指南 | 真实来源产物通过同一契约 |
| P3 网站 | P1 固定样例 | P2、P4 模板和交互文案 | 接入 P2 真实产物后通过独立浏览验收 |
| P4 治理与投稿 | P1 最小格式与治理原则 | P2、P3 | 自动检查接入 P2；公共闭环依赖公开位置决定 |
| P5 消费与兼容 | P1 契约、P2 产物 | P3 后期优化、P4 演练 | 页面和消费者共用事实源，独立性检查通过 |

## 8. 质量与完成规则

每个阶段结束需更新本计划中的状态，记录实际交付、验收证据、已知限制与下一阶段前置条件。不能因为文档已写、页面能打开或一次构建成功就替代整个阶段的完成标准。

验证按变化选择有意义的检查：

- 模型和公共格式：有效/无效样例、关系完整性、旧消费者兼容。
- 采集与生成：固定输入快照、合并优先级、失败保留、重命名和恶意内容。
- 网站：关键用户路径、独立浏览、键盘访问、深链接和静态资源加载。
- 协作与发布：真实权限边界、外部投稿、可信发布入口和回滚演练。
- 文档与计划：任务依赖一致、状态准确、没有把待定项写成已批准决定。

第一版必须通过 A01–A21 中对应已实现范围的验收。任何因未授权公开而无法执行的检查保持未通过/待执行状态，不能以模拟结果宣布公共发布完成。

## 9. 单人工作量规划估计

以下按熟悉静态网站和 GitHub 自动化的一名开发者估算，假设首版保持上述 MVP 范围，试点来源规模有限，不包含外部审核等待、组织沟通和公开授权等待。**这是排期讨论用区间，不是时间承诺，也不是已经投入的工时。**

| 阶段 | 估计工作量 | 主要不确定因素 |
| --- | --- | --- |
| P0 | 0.5–1 人日 | 远端权限、现有同名仓库、规划材料校对 |
| P1 | 3–5 人日 | 真实资源异构性、公开契约范围和技术选型 |
| P2 | 5–8 人日 | GitHub 来源差异、缓存、失效处理和构建边界 |
| P3 | 5–8 人日 | 详情信息层次、筛选体验、移动端和无障碍 |
| P4 | 3–5 人日 | 身份确认、审核规则和实际公共入口 |
| P5 | 3–5 人日 | 契约可消费性、版本引用和兼容问题 |
| P6 | 3–5 人日 | 试点数据修正、部署权限、恢复演练与公开方案 |

合计约 **23–37 人日**，对应约 5–8 个全职工作周的净投入。若为未知情况预留 20%–30%，可按约 6–10 个工作周讨论整体窗口；外部等待另算。P2、P3、P4 可以交错推进，但单人情况下主要减少等待，不能把工作量直接相加后随意压缩。

若主仓库长期私有而新增公共目录仓库，暂预留额外 **2–4 人日**用于权限、同步、兼容和恢复设计及验证，实际以方案确认后的拆解为准。多语言站点、复杂维护者认证、自动运行资源或独立账户体系均会改变估算，应作为新范围重新计划。
