# 目录对象与公开数据契约

> 状态：实施前设计。本文规定拟实现的模型、行为和验收方向；文中的字段、公开文件路径和验证机制尚未实现。P1 确定模型与契约，P2 实现采集和发布流水线，P5 验证独立客户端消费及兼容性。

## 1. 目标与边界

AIPOCH Network 整理现有 GitHub 科研项目和资源，提供独立可用的网站与公开静态目录。现有项目无需迁移仓库、重组文件或安装 AIPOCH 配套工具，即可被基础收录。

本契约遵守以下边界：

- 最小投稿输入是一个公开 GitHub 仓库或组织 URL。用户无需提供完整元数据；无法可靠获得的信息保留未知。
- 基础收录不要求上游存在 AIPOCH 清单、特定 topic、指定许可证或工作台执行配置。公开可读与获准复制、分发、运行分别判断。
- AIPOCH 保存目录、补充描述和来源引用；代码、文档、版本及协作尽量保留在原仓库。
- v1 只接入 GitHub。模型保留来源提供方字段，暂不实现其他平台、通用插件系统或跨平台账号合并。
- 公开契约不使用 Open-Science 的类型、路径、项目格式、唤起协议或测试夹具，也不依赖该应用存在、运行或发布。
- 网站内部搜索数据与公开目录契约分别管理。网站技术栈变化不应改变公开目录的字段含义。

当前仓库先以私有方式规划和开发。本文所述“公开”是未来经项目所有者明确批准后的发布行为，不代表当前已开通公开站点或允许将私有内容复制到公开目录。

## 2. 对象模型

### 2.1 核心对象

| 对象 | 职责 | 建议核心信息 | 不应默认推断的内容 |
| --- | --- | --- | --- |
| `SourceRepository` | 标识实际存放内容的 GitHub 仓库 | AIPOCH ID、GitHub 仓库数字 ID、当前地址、所有者引用、默认分支、来源状态 | 仓库等于一项研究；仓库所有者等于所有论文作者 |
| `Project` | 描述围绕研究问题开展的工作 | 标题、问题或目标、描述、相关来源、资源引用、参与者声明 | 研究已完成、成果有效、所有仓库属于同一机构 |
| `Resource` | 描述可被发现和复用的研究资源 | 类型、用途、来源位置、文档、版本引用、许可证信息、可选输入输出 | 已适配任何客户端、可一键运行、没有额外使用条件 |
| `Actor` | 标识 GitHub 个人账号或组织账号 | AIPOCH ID、GitHub 数字 ID、账号种类、当前名称、公开来源链接 | 自然人实名、机构法定身份、非公开成员关系 |
| `Organization` | `Actor` 中组织账号的科研展示扩展 | 组织简介来源、精选资源、目录策展声明、认领状态 | 被收录就代表合作、背书或已授权组织代表 |
| `Collection` | 表达主题或人工策展集合 | 标题、说明、维护方、条目引用、顺序及选择依据 | 集合成员获得科学验证或维护者认证 |

`Organization` 沿用对应 `Actor` 的身份，不另建与同一 GitHub 组织相互竞争的身份体系。个人科研档案可后续增强；v1 无需独立账户系统。

资源分类首先服务发现，例如工具、方法、工作流、技能、数据资料、模型和复现材料。无法确定类型时使用未知或待分类状态，不为了通过校验强行归类。分类值在 P1 中收敛，并规定客户端遇到未知类别时的通用展示方式。

### 2.2 关系不是一对一

| 关系 | 允许的结构 | 处理原则 |
| --- | --- | --- |
| 来源仓库与研究项目 | 多对多 | 一个项目可以跨仓库，一个仓库可以服务多个项目 |
| 来源仓库与研究资源 | 多对多 | 仓库可以包含多个资源；一个资源也可以引用多个来源，但每个位置分别标明作用 |
| 项目与资源 | 多对多 | 区分使用、产出、参考等关系，不把普通链接统一视为依赖 |
| 个人、组织与条目 | 多对多 | 区分 GitHub 所有者、声明的作者、维护者和目录编辑 |
| 集合与条目 | 多对多 | 集合引用稳定 ID，不复制一份条目形成独立身份 |
| 分叉仓库与上游 | 独立身份之间的关系 | 保留各自 ID；GitHub fork 关系不能直接等同研究复用或科学派生 |

每条有意义的关系应能标明关系类型、来源依据、记录时间，以及必要的适用版本。没有依据的关系不自动补齐。

仅有仓库链接时，先建立来源记录和可展示的目录入口。允许稍后再判断它对应一个研究项目、一个或多个资源；不得为了满足界面需要虚构研究目标、作者关系或执行能力。

## 3. 从一个链接开始收录

### 3.1 最小投稿与后续整理

| 输入或阶段 | 要求 | 未满足时的行为 |
| --- | --- | --- |
| 投稿 URL | 指向公开 GitHub 仓库或组织；文件、目录链接可保留具体位置并归一到仓库 | 不可识别时给出可纠正原因，不创建错误来源身份 |
| 投稿者附言 | 可选：为什么与科研有关、建议分类 | 不影响最小格式有效性 |
| 来源解析 | 确认来源身份与公开可访问性 | 暂时失败保留候选状态，不能把失败当成项目不存在 |
| 元数据采集 | 从公开来源读取可获得的信息 | 描述、许可证、领域、语言或用途可以未知 |
| 目录审核 | 确认来源、科研相关性、描述准确性及是否重复 | 格式有效不等于自动收录；记录收录或退回原因 |
| 后续增强 | 可由社区或维护者提交补充 | 不要求原作者改动仓库，贡献者角色必须清楚 |

组织链接先形成组织候选与可选择的公开仓库列表。默认不把所有现有或未来仓库自动纳入目录。组织维护者可提交明确的策展范围；刷新时新增仓库进入候选，不继承已有项目的审核结论。

### 3.2 收录、读取与运行分别表达

| 维度 | 表达内容 | 约束 |
| --- | --- | --- |
| 收录状态 | 候选、已收录、撤回、被替代 | 表达目录决定，不证明内容有效 |
| 来源可用性 | 可访问、暂时不可用、未知 | 缺少访问权限和来源消失不能仅凭一次错误区分 |
| 内容权限 | 已发现的许可证或使用条件及其来源；也可以未知 | 没有许可证信息不妨碍基础链接收录，但不能据此授予复用权利 |
| 运行描述 | 无运行说明、作者提供说明、社区提供适配说明等 | 提供说明不代表 AIPOCH 执行过或支持某客户端 |
| 运行或验证证据 | 可选的外部记录、适用版本、环境、提交者与结论范围 | 单次运行成功不能转化为整体科学验证通过 |

网站和消费者不得把这些维度压缩成含义不清的统一“已验证”徽标。

## 4. 稳定身份、改名与转移

### 4.1 身份字段方向

| 字段方向 | 用途 | 稳定性规则 |
| --- | --- | --- |
| `id` | AIPOCH 内部及公开引用 ID | 与展示名称、仓库路径和目录文件位置无关；创建后不因改名变化 |
| `provider` | 来源提供方 | v1 固定支持 GitHub；不据此承诺其他平台实现 |
| `provider_id` | GitHub 返回的仓库或账号数字 ID | 与提供方组合用于识别来源，不仅以 owner/name 去重 |
| `canonical_url` | 当前确认的来源地址 | 可以更新，不能被当成永久身份 |
| `aliases` | 已确认的历史地址或展示 slug | 记录验证依据及有效时期；不能无条件把旧 URL 的现内容视为原条目 |
| `source_refs` | 项目和资源的来源关联 | 引用来源 ID，并保存必要的相对路径和版本定位 |

同名仓库被删除后重建，或旧名称被其他账户使用，必须先比较来源 ID。若来源 ID 不同，建立新对象或进入人工核对，不继承旧条目的认领、审核、版本和贡献关系。

仓库改名或转移后，只有确认来源 ID 仍一致，才更新规范地址并保留历史别名。身份一致不代表原组织的策展、成员或代表权限继续有效；这些关系需重新核对。

重复收录合并时，选定保留的 AIPOCH ID，旧 ID 保留最小重定向记录。资源拆分或研究范围变化时可以创建新 ID，并用“替代”“拆分自”等有依据的关系说明，不复用旧 ID 指代另一个对象。

## 5. 三层数据与字段溯源

### 5.1 数据分层

| 层 | 保存内容 | 维护方式 | 边界 |
| --- | --- | --- | --- |
| 来源观察层 | GitHub 公开元数据、指定位置的内容摘取、采集状态与时间 | 流水线刷新；必要时引用固定 commit | 仅记录观察结果，不混入人工编辑意见 |
| 人工补充层 | 科研分类、经过审核的摘要、社区补充、维护者声明、认领及策展决定 | 通过 GitHub 审核流程维护 | 保留作者角色与依据，不伪装成原仓库事实 |
| 派生产物层 | 公开详情、关系、分页或分片数据、网站索引 | 按确定规则构建，可重新生成 | 不接受直接人工修补；发布前过滤私有或不适合公开的材料 |

自动提取只作为来源观察或候选描述；未来若引入模型辅助整理，必须标识其生成方式，不能自动升级为维护者声明。v1 不依赖模型服务才能完成收录和构建。

### 5.2 字段来源应可追踪

| 信息 | 建议记录 | 目的 |
| --- | --- | --- |
| 来源位置 | 提供方、来源 ID、URL、文件路径、必要的 commit | 能返回支持该字段的资料 |
| 来源时间 | 观察时间、声明时间、适用版本 | 区分资料本身的时间与 AIPOCH 采集时间 |
| 提供角色 | GitHub 来源、社区提交、维护者声明、目录编辑、自动提取 | 说明谁对该描述负责 |
| 审核状态 | 待审核、已审核、争议中、过期等 | 审核只覆盖明确范围 |
| 派生依据 | 摘要或分类使用了哪些来源、采用何种规则 | 能解释为何呈现某个字段 |
| 覆盖范围 | 对象、字段、路径或版本 | 避免一个确认扩散为对整个组织的背书 |

公开溯源只包含必要的公开信息。私人身份核验材料、访问令牌、非公开成员查询结果、内部讨论和删除请求中的私人联系方式不得进入公开产物。

### 5.3 冲突优先级按字段确定

不采用“一律人工覆盖”或“一律最新覆盖”的全局规则。

| 字段类别 | 合并规则 |
| --- | --- |
| 仓库或账号身份、当前路径、归档状态 | 以经验证的 GitHub 来源观察为准；人工发现异常可暂停更新，不能编辑为另一个身份 |
| 原始标题、README、原始版本信息 | 保留原始来源含义；展示标题或研究摘要另设字段 |
| 科研领域、适用问题、编辑摘要 | 使用审核后的补充描述，保留依据及提出者角色；自动结果先作为候选 |
| 作者提供的输入输出或运行条件 | 有来源的维护者声明优先用于展示，但与社区实测或争议记录并存 |
| 许可证和使用条件 | 保存来源位置、适用路径与版本；冲突时显示不确定，不由目录编辑授予更宽权限 |
| 所有权、维护权、组织代表权 | 仅由对应核验结果决定；普通条目编辑权不能覆盖身份核验 |
| 复用、验证、协作关系 | 保存各方明确提出的记录与证据，不能由 popularity、topic 或普通超链接替代 |

来源修改后，与旧内容绑定的摘要或声明应标为待复核或保留其旧版本适用范围。短期采集失败不应删除有效人工补充，也不应悄悄把旧快照当成最新事实。

## 6. 社区收录、维护者声明与认领

三者是独立事实：有人提交了一个链接；有人声称某项能力；有人被确认拥有特定维护或代表权限。它们不能互相替代。

| 层次 | 可以表达什么 | 不能表达什么 |
| --- | --- | --- |
| 社区收录 | 某贡献者推荐该来源；目录审核通过 | 原作者参与了 AIPOCH、组织认可 AIPOCH |
| 有来源的维护者声明 | 原仓库公开说明了用途、条件或配置 | AIPOCH 验证了所有技术或科学声明 |
| 仓库维护者认领 | 某 GitHub 身份经核验可代表该仓库的相应维护范围 | 可代表所属组织的所有仓库或机构主体 |
| 组织策展认领 | 某身份经单独核验可管理该组织在目录中的策展信息 | 能代表组织全部成员发表意见，或证明其线下法定地位 |

认领设计应记录主体、被认领对象、授权范围、证据来源、核验时间和失效或复核条件。v1 允许先采用人工审核，不以新增登录后端作为前提。

组织认领必须有明确的组织 owner 权限证据，或由已核验 owner 作出的范围清楚的授权。公开组织成员身份、某仓库提交记录、PR 被合并、仓库写入权限以及组织名称相似都不足以单独证明组织代表权。

实施时优先选择能公开核验且范围最小的证据。如果核验确实需要私有权限查询，应只在认领者主动发起时使用完成该核验所需的最小权限；仅保存核验结果和必要审计信息，不将私有成员清单复制到注册目录。无法获得充分证据时保持未认领，不推断非公开成员或权限，也不为此要求所有组织公开成员身份。

账号重命名、仓库转移、维护权限变化、争议或证据失效都可能触发复核。认领状态不能随来源别名转移给新的账号或仓库。

## 7. 可选增强清单

增强清单用于提高描述质量和机器可读性，属于可选入口。它可以由上游维护者发布在原仓库，也可以由社区在目录侧提供有出处的补充；两者明确标识，不能将社区适配包装为上游承诺。

| 可增强的信息 | 描述边界 |
| --- | --- |
| 资源拆分与定位 | 仓库内有哪些资源，各自文档和文件位置是什么 |
| 科研用途 | 面向的问题、适用领域、方法及限制 |
| 输入输出 | 格式、语义、必要条件与预期产物；未知项可省略 |
| 环境与依赖 | 已声明的工具、版本或运行条件及其依据 |
| 许可证与访问条件 | 引用相应文件或官方说明，不能由清单覆盖原许可证 |
| 版本 | 指向可核验的来源版本、路径及可选校验信息 |
| 运行入口 | 指向现有文档或通用执行说明；不绑定某个客户端内部格式 |

清单格式尚待 P1 定稿，当前不要求特定文件名。解析失败只影响增强信息，不能令本来可读的来源从基础目录消失。清单不得携带凭据或要求采集器执行安装脚本；将其内容视作资料而非对流水线的指令。

第三方客户端负责把这些描述转换为本地可执行配置。AIPOCH 不承诺替任意客户端安装环境、解释专有协议或进行同步发版。

## 8. 最新状态与固定版本

### 8.1 浏览与复用的定位不同

| 场景 | 允许的引用 | 展示和校验要求 |
| --- | --- | --- |
| 发现与浏览 | 当前仓库地址、默认分支、最新可用描述 | 显示观察时间与来源状态，避免将缓存视为实时结果 |
| 阅读某次目录快照 | 目录快照 ID 及其中来源观察 | 快照标识目录当时的记录，不自动固定仓库全部内容 |
| 准备复用或引用具体文件 | 来源 ID、完整 commit SHA、路径，必要时内容摘要 | 客户端应能确定所用文件，不能仅保存可移动的分支或 tag |
| 外部发布附件 | 发布记录、附件标识、下载位置和内容校验值 | 不假定附件永远可下载或仅凭发布标签即可保证内容不变 |

“最新”是发现便利功能；“固定版本”是具体内容定位。把 tag 解析为 commit 时记录解析结果和时间。路径变化时保留原版本路径，不能自动指向新位置并仍称为同一份材料。

commit 和校验值用于识别内容，不保证第三方永久托管、执行成功或科学结论正确。无法定位到固定版本的资源仍可被收录和浏览，但不得标称已满足固定版本复用条件。

### 8.2 三种版本不得混用

- 契约版本决定字段与语义的兼容规则。
- 目录快照版本决定一组目录条目在某次发布中的一致状态。
- 来源内容版本决定实际仓库内容或附件。

消费者需要固定哪一种版本，应由使用场景决定；目录更新不代表原研究成果发布了新版本。

## 9. 公开静态 v1 契约

### 9.1 发布结构方向

拟定公开入口为相对发布根的 `catalog/v1/manifest.json`。该路径当前不存在。入口可变，指向一次完整、已经发布的目录快照；详情、关系和分页数据使用快照内的稳定路径。网站内部搜索索引使用独立位置，不属于此入口承诺的契约。

| 清单字段方向 | 含义 |
| --- | --- |
| 契约版本 | 消费者可判断是否支持当前格式 |
| 快照 ID | 标识本次一致发布的数据集合 |
| 生成时间 | 目录快照产生的时间，不等于所有来源更新时间 |
| 对象集合清单 | 各对象类型的数据位置、分片信息及可选记录数 |
| 分片描述 | 相对 URL、字节数、内容校验值，以及所含对象或分页范围 |
| 状态或撤回信息位置 | 消费者刷新和处理已撤回 ID 所需的最小数据 |

P1 确认详细字段名、日期格式、限制与枚举；P2 实现构建及发布。初期数据量小也采用同一入口，允许一个集合只有一个分片，不为早期规模建立复杂服务。

### 9.2 相对 URL 与分片

契约中的相对 URL 以包含该引用的文件 URL 为基准解析，入口本身相对站点发布根定位。实现不得假定站点部署在域名 `/` 根路径，也不得把 GitHub Pages 仓库子路径写死在消费者中。

契约自身的分片链接应留在预定目录发布范围内；来源 GitHub URL 单独表达为外部来源链接。路径遍历、意外跨域分片和含凭据 URL 应由发布验证拒绝。

消费者根据清单读取分片，不依赖文件名排序、固定分片数量、目录遍历或网站页面结构。分片规则调整不应改变对象 ID；跨分片引用仍引用对象 ID。记录数未知或暂不可提供时明确缺失，不能用零代替。

生成并验证全部快照文件后，再构造指向它们的可变入口；Pages 将入口和快照作为同一份完整静态产物发布，不依赖逐文件在线写入接口。消费者一次读取后应在该快照内完成后续请求，不能混合不同快照的分片。缓存不一致或下载失败时可重试；只有完整验证且未被撤回的上一快照才可用于降级，并显示数据时间。

### 9.3 与网站搜索解耦

网站可以采用自己的压缩、分词、排序和搜索分片。公开消费者不能把这些内部产物当作长期稳定接口。

v1 提供完整或分片的目录读取能力，不承诺动态查询服务器或与网站相同的排序结果。独立消费者可以自行检索；以后若需要稳定的专用搜索数据格式，应单独提出契约，不隐式扩大内部索引的支持范围。

### 9.4 兼容性原则

| 变更 | v1 内处理方式 |
| --- | --- |
| 增加可选字段 | 允许；消费者忽略未知字段 |
| 增加分类值 | 仅在预先规定可扩展的字段允许；消费者按未知类别展示 |
| 改变状态枚举含义、字段类型或必需性 | 视为不兼容变更，发布新契约版本 |
| 改变对象 ID 或引用语义 | 不作为普通字段更新；需要明确迁移和别名规则 |
| 调整分片或文件位置 | 通过入口清单表达，不能要求消费者硬编码位置 |
| 修改网站框架、搜索库或展示路由 | 不影响公开契约 |
| 删除历史契约版本 | 先有独立弃用决定、公告和迁移说明，不因网站重构直接删除 |

v1 的状态字段在发布前固定语义。未知字段与未知分类允许降级，不代表遇到未知的权限、撤回或可执行状态时可以默认放行。

### 9.5 错误、缺失和未知

缺失字段表示没有可发布信息；只有契约明确允许时才使用空值表达特定状态。不得把未知许可证写成“允许使用”、未知作者写成仓库所有者、未知数量写成零。

来源请求失败与目录内容状态分别记录。暂时网络故障、速率限制或权限不明时保留上次有效观察并标记过期，不能把这些情况自动解释为来源删除或转私有。错误信息公开前去除令牌、请求头、内部路径和非公开响应内容。

静态文件缺失、格式不支持、校验失败、引用断裂和撤回分别有明确消费者行为。任何失败都不能促使消费者自动执行原仓库说明中的恢复命令。

## 10. 撤回、不可用与历史快照

普通更新保留可追溯的历史快照；涉及撤回、误公开、来源转私有或其他需清除公开内容的情况，历史保留规则让位于删除策略。这是不可变快照策略的明确例外。

| 情况 | 处理方向 |
| --- | --- |
| 一次采集失败 | 不立即撤回；保留上次有效数据，标记观察失败并安排重试 |
| 来源归档 | 可继续收录，明确归档状态；不推断资源不可用 |
| 来源确定不可公开或有已确认撤回请求 | 停止新的公开采集和展示，按规则清除相关公开派生内容及受影响的历史快照 |
| 条目被合并或替代 | 保留最小替代关系，支持旧 ID 迁移 |
| 涉及敏感信息或误收录 | 优先移除公开副本、缓存和可控历史产物；使用最少必要公开说明 |

撤回 tombstone 仅保留引用完整性需要的信息：稳定 ID、撤回状态、必要时间，以及适合公开时的替代 ID 或通用原因。避免继续保留原描述、作者联系方式、私有化后的地址或具体删除请求内容。

公开快照发布与删除必须覆盖实际托管位置、构建产物和可控缓存。不能因当前仓库仍为私有就默认未来可以直接公开其全部 Git 历史。涉及隐私或误公开时还需检查仓库历史与附件的清理方式。

无法承诺撤回已经被第三方下载、缓存或分叉的副本，也不提供永久删除的虚假保证。消费者刷新目录时应处理 tombstone、停止继续展示被撤回内容，并按自身保存政策清理可控缓存。

## 11. 夹具与验收方向

测试使用独立的合成目录和脱敏 GitHub 响应夹具，不读取 Open-Science 代码、工作区、数据库、测试资料或运行环境。确定性测试不依赖在线 API；少量在线冒烟验证单独运行，避免 GitHub 状态影响基础测试。

| 阶段 | 夹具或场景 | 验收标准 |
| --- | --- | --- |
| P1 | 只有 URL、无 README、无 license、无 topic、无增强清单的仓库 | 最小投稿有效；缺失字段保留未知，仍可进入目录审核 |
| P1 | 一个仓库包含多个资源、一个项目跨多个仓库 | 引用无歧义，不通过复制来源对象绕过多对多关系 |
| P1 | 社区描述与维护者声明冲突 | 保留来源和角色，按字段规则处理，不能静默覆盖 |
| P1 | 同名不同 GitHub 数字 ID、改名、转移及 fork | 新身份不继承旧认领；真实改名保留稳定 ID；fork 不被合并 |
| P1 | 普通成员或仓库写入者尝试代表组织 | 不授予组织认领；私有成员信息不进入公共资料 |
| P1 | 合法、缺失及损坏的可选增强清单 | 增强失败不阻断基础链接收录；输入不触发执行 |
| P2 | 速率限制、短暂断网、不可区分的访问失败 | 保留上次有效快照并标记状态；不误删条目或泄露错误细节 |
| P2 | 默认分支移动、tag 指向改变、固定 commit 和文件校验 | 浏览最新与固定版本明确区分，旧引用不被改写为新内容 |
| P2 | 站点根路径和带仓库子路径的两种部署 | 所有契约相对引用可正确解析，无硬编码域名或根路径 |
| P2 | 分片数量变化、损坏分片、构建中断、入口切换 | 不发布残缺快照，不跨快照混读，消费者可识别失败 |
| P2 | 撤回、转私有、旧 ID 合并 | 当前与历史公开产物按删除策略处理，tombstone 不泄露原内容 |
| P5 | 只读取公开入口的最小独立消费者 | 可遍历对象、解析来源和固定版本，无需安装 Open-Science |
| P5 | 新可选字段、新分类值、旧消费者 | 在已定义扩展规则内继续消费，未知安全状态不会被默认允许 |
| P5 | 网站更换搜索产物或内部路由 | 公共消费者无需同步修改 |

本文仅交付规范方向。后续 P1 按实施计划形成经过评审的字段字典、关系约束、状态规则、校验模式与合成样例；当前 P0 不实现这些代码。P2 证明目录能可靠产生和更新，P5 证明其能被独立消费。任何阶段均不以 Open-Science 集成成功作为 AIPOCH Network 的发布前提。
