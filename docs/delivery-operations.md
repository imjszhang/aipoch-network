# 交付、运行与发布计划

状态：规划基线，尚未实现工作流或发布网站。

官方资料核验日期：2026-09-12。

适用范围：AIPOCH Network 自身的目录采集、静态构建、投稿治理与 GitHub Pages 发布；不依赖 Open-Science 的代码、账号、协议实现或发布周期。

## 1. 当前阶段与可见性边界

当前采用私有仓库研发。此阶段不启用 GitHub Pages，不创建公开预览，不将仓库转为公开，也不创建第二个公开仓库。开发验证使用本地预览；此阶段的 Actions 日志与构建产物继承私有仓库的访问边界，并设置适当保留期。该边界不延续为未来公开仓库的保密承诺。

仓库私有与网站私有是不同设置。GitHub Free 支持公开仓库的 Pages；私有源仓库的 Pages 需要 Pro、Team 或 Enterprise 等适用计划。Pages 网站通常默认公开，即使源仓库私有。访问受限的 Pages 要求 GitHub Enterprise Cloud 组织，并适用于其私有或内部仓库的项目站。[Pages 可用范围](https://docs.github.com/en/pages/getting-started-with-github-pages)、[Pages 默认可见性](https://docs.github.com/en/enterprise-cloud%40latest/pages/getting-started-with-github-pages/creating-a-github-pages-site)、[Pages 访问控制](https://docs.github.com/en/enterprise-cloud%40latest/pages/getting-started-with-github-pages/changing-the-visibility-of-your-github-pages-site)

以上是平台约束核对，不代表已验证当前账户套餐、组织资格或 Pages 设置。首次部署前必须重新核对账户实际能力和当时的平台规则。构建包内的 JSON、source map、图片和隐藏页面都属于发布内容；前端隐藏字段不能形成访问控制。

登录 GitHub 且具有仓库读取权限的用户可以下载 Actions artifacts，工作流日志也面向有读取权限的用户；公开仓库的这些材料不能视为仅维护者可见。GitHub 还明确提示，能对仓库发起 PR 的人可读取相应基础分支缓存，因此公共仓库的日志、artifacts 和 cache 都不作为机密存储。PR 预览的可见性取决于实际承载位置，不能因其属于 PR 就称为私有。[构建产物访问权限](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts)、[日志访问权限](https://docs.github.com/en/actions/how-tos/monitor-workflows/use-workflow-run-logs)、[缓存访问与安全边界](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)

需要保密的审计证据、原始缓存和恢复材料只能留在维护者本地，或另行确认访问控制的私有位置。公共仓库流水线仅持久化经过公开范围检查的数据和报告；工作目录中暂存的原始响应不得自动上传到日志、cache 或 artifacts。本文不新增后台服务或专门仓库，也不预设已经存在私有远端存储。

## 2. 未来公开发布的两种布局

网站公开与社区投稿需要单独确定仓库布局。私有仓库的 Issue/PR 只对具备访问权限的人可用，不能作为无需邀请的社区投稿入口。

| 布局 | 内容与入口 | 优点 | 新增成本与决策 |
| --- | --- | --- | --- |
| 主仓库转为公开 | 网站代码、目录、规范、Issue/PR 和 Actions 集中维护 | 单仓库协作，投稿与构建关系直接，便于复用现有 GitHub 流程 | 这是未来提案，必须由用户明确决定；公开前审查完整 Git 历史、文件、许可和资料，不自动执行可见性变更 |
| 主仓库长期私有，新增公开目录/投稿仓库 | 私有仓库维护网站与构建实现；公开仓库维护允许公开的目录、规范和投稿入口 | 可以保持网站实现私有，同时开放目录治理 | 新建公开仓库也需要明确决定；增加跨仓库访问、触发、版本对应、权限撤销和故障恢复成本 |

第二种布局还需选择 Pages 从何处发布：从私有实现仓库发布时，应核对套餐支持且明确网站会公开；从公开仓库发布时，需要可靠地交接已审查的静态构建产物。两种方式都要防止将私有实现资料或内部采集缓存混入公开仓库与站点。

跨仓库自动化优先考虑权限收敛的 GitHub App 安装令牌；若使用其他凭据，必须记录最小资源范围、持有人、有效期和轮换方式。不要假设一个仓库的 `GITHUB_TOKEN` 可以任意写另一个仓库。创建 PR 或推送后的后续工作流能否触发，应在选定凭据与事件组合后验证，不依赖隐含的事件连锁。[工作流身份认证](https://docs.github.com/en/actions/tutorials/authenticate-with-github_token)、[工作流触发事件](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)

无论选择哪种布局，公开目录协议均由本项目独立版本化，网站内部索引不作为第三方客户端契约。Open-Science 或其他客户端的适配工作不进入本项目的发布门禁。

## 3. Actions 的三个权限域

| 权限域 | 允许的任务 | 凭据和输入边界 | 输出 |
| --- | --- | --- | --- |
| 投稿与代码检查 | schema、分类、引用格式、fixture、静态构建和界面检查 | 外部 PR 按不可信输入处理；默认只读，不提供采集密钥、写入权限或部署权限 | 校验结果和按承载位置确定可见性的预览产物；公共仓库产物须可公开 |
| 来源采集与目录生成 | 获取已批准来源的公开资料、检查公开状态、生成候选快照 | 仅运行受信默认分支上的本项目代码；只使用采集所需的凭据；新增来源需先经过审核 | 临时采集数据、可审查差异、候选快照与采集报告；保密材料按第 1 节存放 |
| 正式发布 | 校验候选快照、组合允许公开的文件、发布及回滚 | 仅受信提交可以进入；部署 job 才获得必要的 Pages/身份权限；以最小权限和发布环境限制执行 | 具备版本和摘要的正式静态站点 |

从 fork 发起的 PR 通常只有只读 `GITHUB_TOKEN`，其他 secrets 不传给 runner。使用 `pull_request_target` 或 `workflow_run` 后检出并执行不可信 PR 代码会引入凭据和仓库写入风险；不采用这种方式绕过 PR 权限边界。第三方 Actions 固定完整 commit SHA，依赖升级经过正常审查。[fork PR 事件与权限](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)、[Actions 安全参考](https://docs.github.com/en/actions/reference/security/secure-use)

采集器只读取研究仓库的数据，不安装或执行来源仓库的包、脚本、Notebook、工作流或二进制文件。README、manifest、Issue 正文和远端文件里的命令属于待解析内容，不能变成运行指令。对外部 URL 使用明确协议与主机约束；凭据不跟随重定向发送到不受信主机。渲染 Markdown 时清洗危险 HTML 和链接，限制文件尺寸及解压行为。

## 4. 周期刷新、缓存与 API 配额

网站和通用客户端主要读取版本化静态数据。访客搜索不直接向 GitHub API 发起逐仓库查询，也不需要登录或提供个人令牌。

建议初期以每日一次刷新为目标，并提供维护者手动刷新入口。该目标不构成准点保证：Actions 定时任务可能延迟或丢弃；定时工作流运行于默认分支，公开仓库在连续 60 天无活动后可能自动停用定时任务。安排在非整点时段，并通过实际运行记录检查是否停止刷新。[定时事件约束](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

采集器需要实现：

- 按来源分配请求预算，使用串行请求队列或经验证的保守并发，遵循分页链接和永久重定向。
- 保存 ETag、Last-Modified、抓取时间、最近一次公开状态检查时间和解析器版本；通过条件请求避免重复获取。
- 限流时读取 `Retry-After`、`X-RateLimit-Remaining`、`X-RateLimit-Reset` 等响应头，指数退避并限制重试次数；不能把限流响应当作仓库删除。
- 请求超时、单来源失败和字段缺失有独立状态；一个来源失败不覆盖其他来源的有效数据。
- 保留具备明确可见性和保留期的采集快照作为恢复基础；需保密的版本只留在维护者本地或已确认的私有位置。Actions cache 仅缓存允许公开的加速材料，不能作为唯一可重建数据来源。
- 不采集私有研究数据；采集使用的凭据即使可以访问私有资源，也必须显式要求来源当前为公开。

核验时的主要 REST 配额为：匿名请求每 IP 每小时 60 次；普通个人认证通常每小时 5,000 次；Actions `GITHUB_TOKEN` 每仓库每小时 1,000 次。搜索端点另有限额，二级限流不能仅靠剩余主配额判断。实际运行应按响应头与账户能力决策，而非把这些数字硬编码为永久承诺。[REST API 限额](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)

GitHub 建议无法使用 webhook 时高效轮询；认证后的未变化条件请求可不计入主限额。限流后持续请求可能导致集成被阻止。[REST API 最佳实践](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)

## 5. 来源失效、转私有与撤回

来源状态和索引新鲜度分别记录。保留最后有效快照用于内部恢复，不代表可以无限期继续公开缓存内容。

| 观测结果 | 内部处理 | 下一次成功发布的处理 |
| --- | --- | --- |
| 已确认公开、内容未变 | 更新检查时间，复用已校验内容 | 正常展示来源和更新时间 |
| 超时、网络故障、5xx 或配额限制 | 标记暂时无法确认，按可见性规则保留快照并重试 | 48 小时后标记软过期；连续超过 7 天仍未核实公开时停止发布摘要等抓取字段，保留最小来源条目 |
| 明确返回 private，或公共读取出现无法解释为限流的 403/404 | 立即标记不可公开访问；不对外断言一定被删除或转私有 | 立即进入下一次发布的清理集合，撤下抓取的标题、描述、README 摘要、图片、版本和派生索引；不等 7 天，也不回退到旧缓存恢复显示 |
| 维护者提出经确认的撤回请求 | 立即登记范围、证据和处理时间 | 立即进入下一次发布的清理集合，从所有公开产物撤回对应内容，不等 7 天，并建立防止下次自动收录的抑制记录 |
| 来源恢复公开 | 重新获取并校验，撤回请求仍需遵守 | 通过正常审核与发布恢复，不自动解除人工撤回 |

MVP 拟定每日尽力刷新，以最近一次成功核实公开为起点，超过 48 小时只标记软过期并提示检查时间，避免一次正常调度延迟导致大面积下架；连续超过 7 天仍无法确认公开，才在下一次发布中停止展示摘要、README 内容、图片、版本等抓取字段。48 小时与 7 天均是待真实配额和运行数据验证的可调运营策略，不是平台保证。明确私有、非限流 403/404 和已确认撤回始终优先清理，不受这一暂时故障宽限期保护。

抓取内容与来源身份分开处理。仅因长期无法核实而收起内容时，可以保留 AIPOCH 条目 ID、此前明确公开的规范来源链接及“暂无法核实”状态，不把最小条目展示为可用或已验证资源。明确不可公开访问或撤回时，最多保留不泄露来源资料的 AIPOCH 条目编号和通用不可用状态；具体链接若也在撤回范围内必须移除。身份声明、简介和编辑摘要若直接派生于已撤回来源，也属于清理范围；详细证据和旧内容只存于维护者本地或另行确认的私有位置。

撤回必须覆盖 HTML、公开目录 JSON、搜索索引、站点地图、图片以及可直接访问的旧快照，并检查公共仓库历史运行的日志、artifacts 和 cache 是否残留应撤回字段。新快照可以保持不可变身份，但公开保留的旧快照必须服从撤回策略；可用撤回声明解释其不再可下载。需保密的历史备份和回滚包仅在维护者本地或另行确认的私有位置保存；公共 Actions 存储不满足这一要求。回滚前重新应用当前撤回清单，不能使旧数据再次公开。

原始采集缓存和历次生成快照不提交到公开仓库历史。公开目录只维护必要的编辑信息与引用；已经进入公开 Git 历史的内容不能仅通过删除当前文件完全收回，因此公开前需要控制保存范围。发现必须处理的历史暴露时，由维护者评估平台支持流程和影响，不自动重写历史，也不承诺能清除所有外部副本。

静态站点只能在发现变化并完成发布后撤回，无法保证仓库改为私有的瞬间同步消失，也无法收回访客已经下载的副本。计划以自动检测、下一次发布清除、人工紧急撤回和可追踪时效处理这一限制，不承诺即时远程擦除。全量刷新失败时保留现有成功站点并报告失败；若涉及已确认的撤回，优先生成只执行撤回的最小发布，必要时由维护者按预先约定的流程暂时停站。

## 6. 可重建快照、发布与回滚

一次发布由三个固定输入组成：目录编辑提交、已获取来源快照、本项目构建工具及依赖版本。每个来源记录 GitHub 标识、来源 URL、解析时使用的 commit 或内容校验值、抓取时间和公开状态；不把可移动的 branch/tag 名当成不可变版本。

候选发布应带有发布 ID、schema 版本、输入清单、文件校验值、采集报告和撤回清单版本。网络请求和时间戳的引入应在快照生成阶段收敛；从同一组固定输入重复构建应得到等价的目录和页面内容。HTML 中需要的构建时间使用记录在快照中的统一时间，避免无法解释的重复差异。

发布顺序为：生成候选快照 → 检查字段公开范围和引用完整性 → 构建网站及静态目录 → 检查部署产物 → 上传完整产物 → 部署 → 冒烟验证。每次只发布同一候选版本的完整目录、页面和索引，使用部署并发限制防止旧任务覆盖新任务。

“原子发布”的项目要求是不得主动把半份新数据混入旧站点；不把托管平台的全球缓存切换视作绝对同步。页面和索引引用具备版本或内容摘要的资源，保留可兼容窗口，并测试缓存混用时的行为。

部署后验证首页、任意项目和资源详情、静态目录版本文件、搜索、来源链接以及不存在页面。失败时重新发布上一份已通过检查的产物，或者重新由固定输入构建；回滚前应用最新撤回和权限规则。回滚演练应在正式公开前使用非敏感测试内容完成。

## 7. Pages 路由、预览和容量预算

React、TypeScript 和 Vite 可生成纯静态产物。项目站路径预计形如 `/aipoch-network/`，Vite 的资源 `base` 需与实际部署路径一致；自定义域名或账户根站则使用根路径。Pages 的服务器行为不能按开发服务器的 history fallback 假设，详情页优先预生成可直接访问的静态文件，搜索条件可以放在 URL 查询参数中。[Vite Pages 部署指南](https://vite.dev/guide/static-deploy.html)

验证环境应使用与 Pages 相似的静态文件服务，并分别检查根路径和项目子路径。验收覆盖直接输入详情链接、刷新、前进后退、分享链接、404、带空格或非 ASCII 查询、静态资源路径以及 JSON 文件的实际可访问性。预览入口应显示其环境属性；任何公开预览都要先确认可见性，不能把“预览”当作“私有”的同义词。

搜索建议采用构建时生成的 MiniSearch 索引，浏览器加载后本地查询；数据规模需适合客户端内存。索引序列化和加载使用相同配置，库内部格式与公开目录协议分开。默认按空白与标点分词，中文及混合科研术语需要独立分词策略和测试。[MiniSearch 适用范围](https://lucaong.github.io/minisearch/)、[索引与分词 API](https://lucaong.github.io/minisearch/classes/MiniSearch.MiniSearch.html)

以下为项目拟定的初期预算，不是已测得结果；达到门槛前用代表性数据集和目标设备校准：

| 项目 | 拟定门槛 | 超出时的处理 |
| --- | --- | --- |
| 静态发布包 | 目标不超过 100 MB，为平台上限保留余量 | 排查图片、重复详情和旧快照；不镜像研究附件 |
| 首次搜索下载 | 压缩后目标不超过 2 MB | 只索引必要字段，延迟加载详情，评估分片 |
| 搜索与移动端内存 | 分别使用 100、1,000、10,000 条代表性 fixture 记录加载、查询和峰值内存 | 依据实测设定设备基线和发布阈值，必要时异步加载或使用 worker |
| 部署过程 | 为平台 10 分钟部署超时保留充分余量 | 将采集与构建放到部署前，定位慢步骤 |

截至核验日期，Pages 发布站点上限 1 GB，部署超过 10 分钟会超时，月带宽软限额 100 GB；普通每小时 10 次构建软限制不适用于自定义 Actions 构建发布。Pages 不适合主要促成商业交易或提供商业 SaaS 的免费托管用途。首次部署时复核这些规则。[Pages 使用限制](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)

研究代码、数据、模型与大文件继续由原项目分发。AIPOCH 只保存为目录检索所需的公开资料、来源引用和最小摘要，不把目录采集扩展为内容镜像。

## 8. 维护者与组织认领：MVP 人工证据

社区收录无需项目方配合，但“被收录”不代表项目方主动加入。认领状态独立于来源公开状态，也独立于研究有效性和复现证据。

| 状态 | MVP 可接受的处理 | 不据此推导的事项 |
| --- | --- | --- |
| 社区收录 | 维护者审核公开来源和描述即可 | 不表示作者、组织同意或背书 |
| 仓库维护者确认 | 核对原仓库默认分支或官方文档中的明确声明、原仓库维护流程中的授权确认，并保存证据 URL | 仓库控制权不代表整个组织授权 |
| 组织官方确认 | 人工核对组织 owner 的确认或可核验的官方组织声明；声明明确覆盖的仓库和展示范围 | 普通组织成员、贡献者身份不自动具备组织代表权 |

组织成员可以隐藏成员关系，公开成员列表不完整；公共成员检查只证明公开成员身份。经适当认证与权限取得的 membership API 可以返回状态和角色，`admin` 对应 owner，但本项目 MVP 不要求建立独立 OAuth 登录或收集组织成员令牌。[组织成员 API](https://docs.github.com/en/rest/orgs/members)

认领记录至少包含：声明主体、范围、证据 URL、证据快照引用、审核人、审核日期、状态与撤销原因。公开记录仅展示必要信息；来源更名、迁移、所有权变化或声明撤回时重新核对。来源变化不自动扩大已确认的组织范围。

## 9. 风险登记与责任

| 风险 | 触发信号 | 预防与恢复 | 首要责任 |
| --- | --- | --- | --- |
| 私有资料进入公开站点 | 构建产物包含内部缓存、私有来源或未经确认的预览 | 公开字段白名单、产物检查、部署可见性门禁；撤回发布 | 发布维护者 |
| 外部输入获取凭据或执行权限 | PR 请求写权限，来源文件包含执行指令 | 三权限域隔离，不执行来源代码；撤销并轮换受影响凭据 | 自动化维护者 |
| 来源转私有后仍展示旧内容 | 非限流的访问拒绝、404 或撤回请求 | 禁止旧缓存回退，清理所有公开产物，应用回滚撤回规则 | 目录维护者 |
| 配额耗尽或周期任务停止 | 限流响应、最近成功刷新超出目标 | 条件请求、退避、手动刷新、明确过期状态 | 自动化维护者 |
| 错误认领或科学背书混淆 | 仅凭账号、成员或收录状态展示官方认证 | 人工证据、确认范围、状态分离、申诉和撤销 | 目录维护者 |
| 子路径、缓存或版本混用导致页面失效 | 详情刷新 404、索引引用错误版本 | 静态环境端到端验证、版本资源、完整产物发布和回滚 | 网站维护者 |
| 长期私有布局增加运行复杂度 | 跨仓库触发未发生、权限不足、版本不对应 | 独立事件契约、权限审计、交接回执及手动恢复 | 发布维护者 |

初期可以由同一维护者承担多个责任，但每次正式发布仍需保留明确的提交、结果和操作者记录。运行失败优先使用 GitHub 现有检查结果、Actions 记录和维护者通知，不引入必须常驻的外部监控服务。

## 10. 发布门禁

### 私有研发阶段

- [ ] 仓库保持私有，Pages 未启用，没有公开预览或公开数据产物。
- [ ] 公开来源 fixture、目录编辑资料、采集缓存和生成产物在结构上分离。
- [ ] 离线 schema、构建与界面检查不需要 Open-Science 或个人 GitHub 凭据。
- [ ] 外部来源不可执行，PR 校验不依赖部署或采集 secrets。

### 首次公开发布前

- [ ] 用户已明确决定公开发布范围和仓库布局；未将计划文档当作改变仓库可见性的授权。
- [ ] 实际账户套餐、Pages 资格、仓库和预览可见性已复核；日期和结论已记录。
- [ ] 公开仓库日志、artifacts、cache 和 PR 预览均按实际可见性审查；保密审计与恢复材料已留在维护者本地或另行确认的私有位置。
- [ ] 确定可访问的投稿入口，说明提交、审核、收录、撤回和认领规则。
- [ ] 核对允许公开的文件、历史、许可说明、图片和第三方引用；公开内容保留来源及必要归属。
- [ ] 来源当前公开状态检查、失效与撤回清理、限流恢复都有通过的测试。
- [ ] 暂时故障按 48 小时软过期和超过 7 天收起抓取字段的拟定策略验证；明确私有、非限流 403/404 与已确认撤回在下一次发布清除，不等待宽限期。
- [ ] 公开 schema 与静态目录独立版本化，网站搜索索引未被误用为客户端稳定接口。
- [ ] 根路径和 Pages 子路径、详情直达、搜索、404、移动端及键盘使用通过验证。
- [ ] 三权限域、Secrets 范围、第三方 Actions 固定引用及跨仓库触发行为已核验。
- [ ] 完整产物部署、失败恢复、回滚和撤回优先于回滚的流程完成演练。
- [ ] 发布包、搜索体积和 API 消耗有实际测量，满足经校准的项目预算。

### 每次后续发布

- [ ] 固定输入、公开字段、来源状态、schema 与链接检查通过。
- [ ] 应用最新撤回清单，不在旧文件、索引或回滚产物中重新暴露内容。
- [ ] 本次站点、索引和目录 JSON 来自同一候选版本。
- [ ] 成功发布后冒烟检查通过；失败时已有可执行的恢复路径。
- [ ] 记录快照 ID、源码提交、部署结果、已知失效来源和下一次维护事项。
